# Спецификация системы оркестрации ИИ-агентов

## 1. Общее описание и цель системы

Веб-система оркестрации ИИ-агентов (CLI-утилит, работающих по подпискам) для полного цикла разработки фич под Unity: от написания и ревью технической документации до реализации кода на локальной машине с Unity, ревью изменений и контроля влития PR в main.

**Ключевые архитектурные принципы:**

1. **Гибридная топология:**
   - **Главный сервер (VDS Ubuntu / локальный WSL2 для тестов):** Хранит БД, веб-интерфейс и все текстовые артефакты. Локальный клон Git-репозитория на VDS отсутствует — облачные/серверные CLI-агенты читают кодовую базу и PR через подключённые Skills / MCP / GitHub CLI (`gh`).
   - **Локальный воркер (ПК разработчика с Unity Editor):** Лёгкий клиентский демон (`unity_worker.py`), подключающийся к VDS по исходящему WebSocket. Выполняет исключительно этап реализации кода в изолированных git worktree с доступом к Unity.
2. **Нулевой перерасход токенов:** Все промежуточные версии документов, замечаний и логов хранятся на бэкенде VDS (`storage/tasks/{id}/`). Агентам в промпте передаются только пути к нужным файлам текущей итерации.
3. **Учёт токенов:** На каждом запуске этапа и на переходах графа фиксируется количество потраченных токенов (`input_tokens`, `output_tokens`).
4. **Событийная синхронизация (Webhooks):**
   - Уточняющие вопросы бота по ТЗ отправляются в комментарии внешнего таск-трекера людей; ответ возвращается в пайплайн по вебхуку.
   - Зависимые задачи стартуют строго после получения Git-вебхука о реальном влитии (Merge) родительского PR в ветку main.

## 2. Рекомендуемый технологический стек

- **Backend (VDS / WSL2):** Python 3.11+, FastAPI, Uvicorn, SQLite (в режиме WAL), websockets / FastAPI WebSockets, SSE (Server-Sent Events) для стриминга логов.
- **Local Worker (PC с Unity):** Python 3.11+, websockets, asyncio (запуск CLI и управление git worktree).
- **Frontend:** React 18+, TypeScript, Vite, Tailwind CSS, React Flow (`@xyflow/react`) для визуализации графа и кастомных плашек на стрелках.

## 3. Функциональные требования: Фронтенд (UI)

Интерфейс состоит из верхней навигационной панели (переключение вкладок + индикатор статуса подключения Unity Worker: Online/Offline) и трёх основных разделов.

### 3.1. Вкладка 1: «Задачи» (Таск-трекер и зависимости)

Интерактивная таблица всех задач с фильтрами (Все, В работе, Ожидают, Готово к PR, Завершены), поиском и кнопкой + Новая задача.

**Столбцы таблицы:**

1. **ID:** Уникальный номер (#101).
2. **Название таска:** Заголовок задачи (клик открывает Вкладку 2: Граф для этой задачи).
3. **Этап:** Цветной бейдж текущего состояния:
   - 0. Ожидает влития в main (Серый с замком 🔒 — ждёт мержа родительских задач).
   - 1. Тех. документация (Жёлтый / Зелёный).
   - 1.5. Ожидает ответа по ТЗ (Оранжевый ❓ — бот задал вопросы в таск-трекере людей).
   - 2. Ревью документации (Синий / Красный при возврате).
   - 3. Реализация (Жёлтый — выполняется на локальном Unity-воркере).
   - 4. Ревью реализации (Синий / Красный при возврате).
   - 5. Готово к PR (Фиолетовый — ждёт мержа PR человеком).
   - 6. Завершено (Зелёный — PR смержен в main).
4. **Исполнитель:** Отображаются только Аватарка и Имя текущего назначенного бота (или [Иконка] Человек на 5-м этапе; —, если задача заблокирована).
5. **Зависимости:** Список родительских задач в виде индикаторов с чекбоксами прямо в ячейке:
   - [✓] #101 Базовая сцена — родительский PR уже смержен в main.
   - [ ] #102 Контроллер игрока — родительский PR ещё не смержен (текущая задача заблокирована).

**Модальное окно создания / редактирования задачи:**

- Название и описание (ТЗ).
- ID / ссылка на задачу во внешнем таск-трекере людей (необязательно, например PROJ-452).
- Зависимости: Мультиселект-список существующих задач с кликабельными чекбоксами (с валидацией от циклических зависимостей).
- Назначение ботов на этапы 1–4 (подставляются дефолтные из настроек, можно переопределить для конкретной задачи).

### 3.2. Вкладка 2: «Граф задачи и Инспектор артефактов»

Разделённый экран (Split View): слева (70%) — граф на React Flow, справа (30%) — инспектор выбранного узла или стрелки. Сверху — селектор быстрого переключения между задачами и бейдж суммарно сожжённых токенов по задаче.

**Узлы графа (5 основных этапов):**

1. **Узел 1:** Тех. документация (Бот 1, среда: VDS).
2. **Узел 2:** Ревью документации (Бот 2, среда: VDS).
3. **Узел 3:** Реализация (Бот 3, среда: Local Unity Worker).
4. **Узел 4:** Ревью реализации (Бот 2, среда: VDS).
5. **Узел 5:** PR (Человек) (Ожидание мержа в main).

**Содержимое карточки узла:** Название этапа, Аватарка + Имя бота, индикатор статуса (Ожидает / В работе + таймер / Возврат / Пройден / Ждёт ответа в трекере / Сработал Fallback), счётчик сожжённых токенов на этом этапе (🔥 18.4k tok).

**Интерактивные плашки на стрелках (Custom Edge Labels):**

На каждой стрелке отображается кликабельный бейдж с переданным артефактом и объёмом токенов за итерацию:

- 1 → 2: 📄 `tech_doc_v{N}.md` • 12.1k tok
- 2 ↩ 1 (возврат при `REJECTED`): 💬 Правки по доке (×{N}) • 4.3k tok
- 2 → 3 (при `APPROVED`): ✅ Дока утверждена (v{N})
- 3 → 4: 💻 Git Diff (+{files}) + Отчёт • 45.0k tok
- 4 ↩ 3 (возврат при `REJECTED`): 🐞 Правки по коду (×{N}) • 6.8k tok
- 4 → 5 (при `APPROVED`): 🚀 Ветка `feat/task-{id}` • Сборка OK

**Правая панель (Инспектор):**

При клике на узел или стрелку отображает:

1. **Где что лежит (Пути и ссылки):**
   - Ссылка на ветку / Draft PR в Git.
   - Локальный путь worktree на ПК с Unity (для Шага 3).
   - Путь к файлу артефакта на VDS (`storage/tasks/{id}/...`).
2. **Просмотр артефакта (с переключателем версий v1, v2...):**
   - Рендер Markdown тех. документации.
   - Блок «Вопросы и ответы по ТЗ» (если Бот 1 задавал вопросы в трекер людей + форма ручного ответа на случай отсутствия вебхука).
   - JSON-вердикт ревьюера (`APPROVED` / `REJECTED`) со списком замечаний.
   - Отчёт о реализации и `git diff --stat`.
   - На Шаге 5: ссылка на PR и резервная кнопка «Подтвердить Merge вручную» (на случай, если вебхук не настроен).
3. **Расход токенов:** Детализация Input / Output / Cache по каждой попытке и использованной модели.
4. **Live Logs:** Поток консоли (stdout/stderr) активного CLI-агента в реальном времени (через SSE).
5. **Ручное управление:** Кнопки «Перезапустить этап» и «Апрувнуть шаг принудительно».

### 3.3. Вкладка 3: «Настройка ботов и Интеграции»

#### Секция А: Профили ботов (карточки + модальное окно редактирования)

1. **Имя бота** (текст).
2. **Аватарка** (загрузка изображения или выбор из встроенных иконок).
3. **Роль (Системный промпт):** Многострочное поле с инструкциями, которые добавляются в контекст при запуске.
4. **Лимит одновременных задач (Concurrency Limit):** Число (по умолчанию 1). Если бот занят, новые задачи встают в очередь к нему.
5. **Основная модель (Primary):**
   - CLI-утилита: Claude Code | Codex CLI | Gemini CLI | Aider | Custom CLI.
   - Идентификатор модели (например, `claude-sonnet-4-6`, `gpt-5-codex`, `gemini-2.5-pro`).
   - Среда выполнения: Server (VDS) или Local Worker (Unity PC).
6. **Резервные модели (Fallback Chain):** Упорядоченный список (Drag-and-Drop) запасных связок (CLI + Модель + Среда).
7. **Триггеры переключения на резерв (чекбоксы):**
   - ☑ Исчерпан лимит подписки / Rate Limit
   - ☑ Ошибка выполнения CLI (Exit Code != 0)
   - ☑ Таймаут выполнения (поле ввода минут, например 20).

#### Секция Б: Настройки интеграций и Webhooks

- URL и Secret-токен для приёма Git-вебхуков (`POST /api/webhooks/git`).
- URL и Secret-токен для приёма вебхуков от таск-трекера людей (`POST /api/webhooks/tracker`).
- Настройки подключения к таск-трекеру людей (провайдер: GitHub Issues / Jira / Linear / YouTrack / Custom API, Base URL, API Token).
- Токен авторизации для подключения локального `unity_worker.py` по WebSocket.

## 4. Архитектура бэкенда и протоколы работы

### 4.1. Структура файлового хранилища на VDS

```text
orchestrator/
├── backend/                  # FastAPI приложение, диспетчер, парсеры
├── frontend/                 # Собранный React-бандл
├── worker/                   # Скрипт unity_worker.py для установки на ПК с Unity
├── storage/
│   ├── orchestrator.db       # SQLite база данных
│   ├── avatars/              # Загруженные аватарки ботов
│   └── tasks/
│       └── {task_id}/
│           ├── 00_task.md
│           ├── 01_tech_doc_v1.md
│           ├── 01_questions_v1.json
│           ├── 01_answers_v1.md
│           ├── 02_doc_review_v1.json
│           ├── 03_impl_report_v1.md
│           ├── 04_code_review_v1.json
│           └── logs/
│               └── stage_{stage}_attempt_{N}.log
└── .env
```

### 4.2. Схема базы данных (SQLite)

1. `agents`: `id`, `name`, `avatar_url`, `role_prompt`, `concurrency_limit`, `primary_config` (JSON), `fallback_configs` (JSON array), `fallback_triggers` (JSON).
2. `tasks`: `id`, `title`, `description`, `external_issue_id`, `current_stage` (0..6), `status` (`blocked_main`, `queued`, `running`, `waiting_answer`, `waiting_pr`, `done`, `error`), `branch_name`, `pr_url`, `merged_to_main` (bool), `retry_count`, `stage_agents` (JSON маппинг этапов 1–4 на `agent_id`), `created_at`.
3. `task_dependencies`: `task_id` (PK, FK), `depends_on_task_id` (PK, FK).
4. `stage_runs`: `id`, `task_id`, `stage`, `attempt`, `agent_id`, `cli_used`, `model_used`, `is_fallback` (bool), `artifact_path`, `input_tokens`, `output_tokens`, `status`, `started_at`, `finished_at`.

### 4.3. Форматы служебных JSON-артефактов (контракт для промптов CLI)

Оркестратор инструктирует CLI-агентов записывать структурированные результаты в строго заданные JSON-файлы:

1. **Вопросы по ТЗ (`01_questions_v{N}.json` от Бота 1):**

   ```json
   {
     "has_questions": true,
     "questions": ["Вопрос 1...", "Вопрос 2..."]
   }
   ```

   Если `has_questions: true`: задача переходит в статус 1.5. Ожидает ответа по ТЗ, вопросы публикуются в комментарий `external_issue_id`. При получении вебхука с комментарием человека ответ сохраняется в `01_answers_v{N}.md`, и Бот 1 перезапускается с указанием пути к ответам.

2. **Вердикт ревью (`02_doc_review_v{N}.json` и `04_code_review_v{N}.json` от Бота 2):**

   ```json
   {
     "status": "APPROVED" | "REJECTED",
     "summary": "Короткая причина для плашки на стрелке (до 60 символов)",
     "comments": ["Замечание 1", "Замечание 2"]
   }
   ```

### 4.4. Протокол взаимодействия VDS ↔ Local Unity Worker (WebSocket)

1. **Подключение:** `unity_worker.py` устанавливает постоянное WebSocket-соединение `ws://{VDS_HOST}/ws/worker` с заголовком `Authorization: Bearer {WORKER_TOKEN}` и шлёт heartbeat каждые 10 секунд.
2. **Выдача задания (`ASSIGN_TASK`):**
   - VDS отправляет JSON: `task_id`, `branch_name` (`feat/task-{id}`), `tech_doc_content`, `review_comments_content` (если был возврат), `agent_config` (primary + fallback цепочка).
3. **Исполнение на ПК с Unity:**
   - Воркер проверяет/создаёт изолированный git worktree от свежего `origin/main` (с использованием симлинка/junction на эталонную папку кэша Library для быстрой инициализации Unity и мьютекса на запуск `Unity.exe -batchmode`).
   - Запускает локальный CLI-агент, транслирует строки stdout/stderr на VDS в реальном времени (`LOG_CHUNK`).
   - При срабатывании триггера ошибки/лимита переключается на следующую модель из `fallback_configs`.
   - После успешного завершения делает `git add`, `git commit`, `git push origin feat/task-{id}` (и создаёт Draft PR через `gh pr create --draft`, если ещё не создан).
   - Отправляет на VDS сообщение `TASK_COMPLETED` с отчётом, статистикой токенов и ссылкой на PR.
4. **Очистка (`CLEANUP_WORKTREE`):** После получения VDS вебхука о мерже PR в main, сервер отправляет воркеру команду удалить локальный worktree и ветку.

### 4.5. Детектор токенов и лимитов подписки

- **Подсчёт токенов:**
  1. Приоритетно используются флаги структурированного вывода CLI (например, `--output-format json` / `stream-json` для Claude Code) и регулярные выражения для парсинга финальной статистики сессии Codex / Gemini CLI.
  2. Если CLI не вернул статистику, выполняется fallback-подсчёт через `tiktoken` по объёму входных артефактов и выходного текста/diff (в UI помечается символом ~).
- **Детектор Rate Limit:** Поток вывода CLI проверяется в реальном времени на паттерны исчерпания подписки (rate limit, usage limit, quota exceeded, 429, try again later). При совпадении процесс корректно завершается и запускается следующая модель из `fallback_configs` бота.

## 5. План поэтапной реализации (Roadmap для разработки)

1. **Этап 1 (База и API):** Инициализация проекта, схема SQLite, CRUD API для ботов (`agents`), задач (`tasks`) и зависимостей (`task_dependencies`), защита от циклов в зависимостях.
2. **Этап 2 (Раннер VDS и парсеры):** Реализация CLIRunner на VDS с поддержкой headless-запуска CLI, парсингом токенов, fallback-цепочками и стримингом логов по SSE.
3. **Этап 3 (Webhooks и Интеграции):** Эндпоинты `/api/webhooks/git` (отслеживание Merge в main и разблокировка дочерних задач) и `/api/webhooks/tracker` (цикл вопросов-ответов по ТЗ).
4. **Этап 4 (Local Unity Worker):** Написание `unity_worker.py` с WebSocket-клиентом, управлением git worktree + симлинком Library и исполнением Шага 3.
5. **Этап 5 (Фронтенд):** Сборка интерфейса на React + TypeScript + React Flow (Таблица задач с чекбоксами зависимостей, Граф с плашками артефактов и токенов, Инспектор, Конструктор ботов).
